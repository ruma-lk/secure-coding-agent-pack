# Payment gateways: mandatory cross-stack security policy

Applies to React, React Native, Flutter, Laravel, PHP, Node.js, Python, Java, Go, Ruby, and any other stack. Also read universal.md, rate-limits-and-abuse.md, and concurrency-and-resource-safety.md. For card data use PCI DSS scope and qualified review; do not assert compliance.

## Identify integration before writing code
Determine provider, merchant account and environment, actual product (redirect/hosted page/hosted session/JS/tokenization/server-to-server), acquiring bank, API version, sandbox/live credentials, documented payment status semantics, callback methods, endpoint allowlists and approved refund/capture capabilities. If unspecified, request current merchant-specific documentation. Never invent signed field order, authentication headers, signature formulas, IP allowlists, 3DS requirements or settlement states.

## Hard security gates
1. **Merchant-controlled payment intent:** Create immutable internal order/amount in integer minor units or exact decimal. Currency, merchant ID, products, discount, taxes, shipping, tenant, user and expiry derive from server state. Never trust browser/mobile values as authority.
2. **Server-authoritative settlement:** Browser return/success/cancel redirects and client SDK events never mark an order paid. Verify genuine gateway notification through the actual documented scheme AND/OR trusted authenticated server-side order/transaction status retrieval as mandated by the gateway. Check merchant, order, transaction, currency, full exact amount and terminal success state; explicitly distinguish AUTHORIZED from CAPTURED/PAID, pending, reversed and failed.
3. **Webhook safety:** Check raw-body signature/required checksum exactly as documented, using constant-time comparison where applicable, correct byte/encoding/casing and credential version. Ensure timestamp/replay protection where provider supports it; durable deduplication for all gateways. Never fabricate a generic HMAC rule for gateways using another scheme. Network IP allowlist is defense in depth, never the only proof.
4. **Atomic state transitions:** Persist separate payment attempt and order records with unique gateway transaction references and database constraints. Handle duplicate/out-of-order notifications, network timeouts, parallel callbacks, failed-to-success/reversal states. Lock or use compare-and-set transactions; only grant tickets/products/access once.
5. **Safe retry:** Separate network retry from business transaction creation. Always use provider idempotency key/unique order reference where supported. Before retrying uncertain capture/charge, query actual provider status; no blind double debit.
6. **Authorization/capture/refund:** Check roles and amounts on every endpoint; refund only eligible captured transactions and enforce remaining refundable balance, reason, audit actor and idempotency. Restrict recurring/MIT/COF charges to documented consent and transaction linkage.
7. **Card security:** Prefer provider-hosted checkout/tokenization. Never store CVV or plaintext PAN; minimize PCI scope. Store only necessary protected gateway tokens, masked last4 where appropriate, expiry metadata and consent artifacts. Protect encryption keys, TLS, logs and backups. Never expose server gateway secrets to React, React Native or Flutter bundles.
8. **Fraud and resource controls:** Rate-limit payment creation/status/refund, login, card testing, retries, webhooks and reconciliation; set per-user/tenant/IP/device ceilings where risk-appropriate. Bound queues, threads, HTTP timeouts and worker concurrency. Monitor anomalies, dispute signals, duplicate charges, failures and reconciliation differences.
9. **Reconciliation:** Independently reconcile local ledger with gateway transaction status, captures, refunds, chargebacks and settlements. Repair ambiguous pending states with explicit audit trail and no duplicate fulfillment. Distinguish paid from settled-to-bank.
10. **Testing:** Test forged callback, modified amounts/currency/order, invalid signatures, redirect-only success, duplicate/out-of-order callback, concurrency races, network timeout during capture, refund escalation, expired tokens, 3DS challenge/failure and rollback. Use sandbox/fakes. Never charge real cards or trigger production refunds without authorization.

## Required evidence per payment integration
Provider + API version, merchant environment, callback validation method and citation to official provider docs, authoritative status API, exact success criteria, state machine, idempotency keys, concurrency/rate bounds, fraud controls, refund access model, reconciliation, tests executed, unresolved risks. Mark not verified as NOT RUN.
